1. プロジェクト概要
==================================================

プロジェクト名:
富山市 新規営業許可施設ウォッチャー

目的:
富山市が公開している「食品営業許可施設」オープンデータを利用し、最近新たに営業許可を受けた食品関係施設を、市民、地域メディア、地域事業者などが検索・閲覧できるWebアプリを構築する。

データセットページ:
https://opdt.city.toyama.lg.jp/dataset/seikatsu-eisei01

現時点で確認できるデータ項目:
・業種
・細分類
・施設名
・施設住所
・ビル名
・営業者名
・許可番号
・許可年月日
・有効年月日

重要な表現上の注意:
このデータから直接確認できるのは「営業許可を受けた日」であり、実際の開店日ではない。

そのため、画面上の正式名称は原則として次のいずれかを使用すること。

・新規営業許可施設
・最近許可された施設
・新たに営業許可を受けた施設

「新規オープン店」「開店日」「オープン日」と断定して表示しないこと。

サービスの愛称として「新規オープン店ウォッチャー」を使う場合は、画面上部に次の注意書きを表示すること。

「本サイトでは、新たに営業許可を受けた施設を紹介しています。許可年月日は実際の開店日とは異なる場合があります。」

4. アプリケーションの基本機能
==================================================

4.1 トップページ

次の内容を表示する。

・サービス名
・サービスの概要
・データに関する注意書き
・データ基準日
・元データの更新確認日時
・掲載施設数
・最近許可された施設数
・業種別件数
・最新の施設カード
・検索画面への導線
・データ出典
・ライセンス表記

「最近」の既定値は、データに含まれる最新の許可年月日を基準とした直近90日間とする。

ブラウザの現在日だけを基準にすると、データ更新が止まった場合に0件になるため、次の基準を採用する。

基準日:
有効な許可年月日の最大値

最近の施設:
基準日から90日前以降の許可年月日を持つ施設

利用者が期間を次から変更できるようにする。

・30日
・90日
・180日
・1年
・すべて

4.2 施設一覧

施設をカードまたは一覧形式で表示する。

各施設に表示する項目:
・施設名
・業種
・細分類
・施設住所
・ビル名
・許可年月日
・有効年月日
・最近追加された施設であることを示す表示
・詳細ページへのリンク

営業者名と許可番号については、元データに含まれていても、初期画面では目立たせない。詳細ページまたは「詳細情報を表示」で確認できる設計とする。

一覧の並び順:
・許可年月日の新しい順
・許可年月日の古い順
・施設名の昇順
・業種の昇順

既定値:
許可年月日の新しい順

同じ許可年月日の場合:
施設名の昇順で安定的に並べる。

4.3 検索

次の項目を対象に部分一致検索する。

・施設名
・施設住所
・ビル名
・業種
・細分類

要件:
・前後の空白を除去する。
・連続する空白を1文字として扱う。
・英数字については大文字と小文字を区別しない。
・全角英数字を可能な範囲で正規化する。
・複数語が入力された場合はAND検索とする。
・検索結果件数を表示する。
・0件の場合は、条件を変更する案内を表示する。

4.4 絞り込み

次の絞り込みを実装する。

・業種
・細分類
・許可年月日の期間
・住所キーワード
・最近許可された施設のみ
・前回データから追加された施設のみ

複数条件はAND条件とする。

「条件をリセット」ボタンを実装する。

選択した条件はURLのクエリパラメータに反映し、URLを共有した場合に同じ検索状態を再現できるようにする。

例:
?keyword=カフェ&category=飲食店営業&period=90

クエリパラメータが不正な場合は、安全な既定値へ戻す。

4.5 施設詳細

施設詳細ページを実装する。

URL例:
#/facilities/{id}

GitHub Pagesで直接アクセスした場合の404問題を避けるため、初期実装ではHashRouterを使用する。

表示項目:
・施設名
・業種
・細分類
・施設住所
・ビル名
・営業者名
・許可番号
・許可年月日
・有効年月日
・元データの基準日
・データに関する注意書き

住所から外部地図を開くリンクを設置する。

外部地図URLは、入力住所を必ずencodeURIComponentでエンコードして生成する。

地図リンクは新しいタブで開き、rel="noopener noreferrer"を指定する。

詳細ページのIDは、配列番号を使用しない。データ更新後も可能な限り同一施設を識別できる安定IDを生成する。

ID生成の候補:
・許可番号
・許可番号、施設名、住所を連結した値のハッシュ

許可番号が欠損または重複する可能性を考慮し、最終的には正規化済みの次の項目から決定的IDを生成する。

・許可番号
・施設名
・施設住所
・業種
・許可年月日

同じ入力なら常に同じIDになること。

4.6 ダッシュボード

次の集計を表示する。

・総施設数
・最近30日、90日、180日の許可件数
・業種別件数
・許可年月別件数
・住所の町名単位での件数

重要:
町名抽出は完全な住所解析ではなく簡易集計であると明記する。

グラフライブラリを使用する場合は、アクセシビリティを考慮し、グラフと同内容の表を併記する。

グラフが表示できない場合でも、集計値を表で確認できること。

4.7 差分表示

current.jsonとprevious.jsonを比較し、次を分類する。

・追加
・削除候補
・変更
・変更なし

重要:
データから消えた施設を「閉店」と断定しない。

表示名称:
・前回データから追加
・前回データから掲載がなくなった施設
・登録内容が変更された施設

注意書き:
「掲載がなくなった理由は、閉店、許可更新、データ修正、掲載条件の変更など複数の可能性があります。本サイトでは理由を特定できません。」

差分判定では、次の考え方を採用する。

第一一致キー:
正規化した許可番号

許可番号が使用できない場合の代替一致キー:
正規化した施設名 + 正規化した施設住所 + 正規化した業種

一致したレコードの各表示項目が異なる場合:
変更として扱う。

変更内容:
項目ごとに変更前と変更後を保持する。

差分生成ロジックはscripts側に実装し、生成結果をdata/diff.jsonへ出力する。

4.8 お気に入り

ブラウザのlocalStorageを利用する。

機能:
・施設のお気に入り登録
・お気に入り解除
・お気に入り一覧
・掲載データから施設がなくなった場合の表示

localStorageが利用できない場合:
アプリをクラッシュさせず、お気に入り機能が利用できないことを表示する。

localStorageのキーにはアプリ名とバージョンを含める。

例:
toyama-permit-watcher:favorites:v1

4.9 新着確認

前回訪問時に利用者が確認したデータバージョンをlocalStorageに保存する。

新しいdataVersionを検出した場合:
「データが更新されました」と表示する。

前回訪問以降に追加された施設数を表示できる場合:
件数を表示する。

通知はブラウザのPush通知ではなく、サイト訪問時の画面内通知とする。

4.10 データ出典ページ

次を表示する。

・データ名称
・提供者
・データセットページへのリンク
・ライセンス
・アプリ側の加工内容
・更新確認日時
・免責事項

加工内容:
・XLSXからJSONへの変換
・文字列の正規化
・日付形式の正規化
・安定IDの付与
・前回データとの差分生成
・期間別、業種別の集計

データの正確性を保証するような表現をしない。

5.2 JSONデータ形式

Facility型を定義する。

必須フィールド:
・id: string
・businessType: string
・subCategory: string
・facilityName: string
・address: string
・buildingName: string
・operatorName: string
・permitNumber: string
・permitDate: string | null
・expirationDate: string | null
・sourceRowNumber: number
・searchText: string

日付形式:
有効な日付はYYYY-MM-DD形式に統一する。

不正または空の日付:
nullとする。

元データをそのまま保持する必要がある場合:
rawPermitDate、rawExpirationDateなどの項目を別途持たせてよい。

metadata.json:
・datasetName
・provider
・datasetUrl
・sourceFileUrl
・license
・downloadedAt
・generatedAt
・dataVersion
・recordCount
・validPermitDateCount
・invalidPermitDateCount
・sourceFileHash
・schemaVersion

dataVersion:
元ファイルのSHA-256ハッシュの先頭12文字など、内容から決定的に生成する。

実行日時だけでdataVersionを作らない。

5.3 XLSX解析

XLSXのシート名、ヘッダー行、列名が将来変更される可能性を考慮する。

最初にinspect-workbook.tsを実装し、次を出力できるようにする。

・シート名一覧
・各シートの行数と列数
・先頭10行
・ヘッダー候補
・空行数

列名は完全一致だけに依存せず、明示的な候補リストで対応する。

例:
施設名候補:
・施設名
・営業施設名

住所候補:
・施設住所
・住所
・所在地

ただし、未知の列を推測だけで誤って割り当てない。

必須列が見つからない場合:
・処理を失敗させる。
・見つかった列名をエラーに含める。
・期待する列名候補をエラーに含める。

部分的に欠損した行:
・施設名も住所も許可番号も空の場合は除外する。
・それ以外は保持し、欠損値を空文字またはnullに正規化する。

セル値:
・文字列
・数値
・Excel日付シリアル値
・JavaScript Date
の可能性を考慮する。

Excel日付の変換ロジックには単体テストを作成する。

5.4 文字列正規化

normalizeText関数を作る。

処理:
・nullとundefinedを空文字にする。
・Unicode NFKC正規化を行う。
・前後の空白を削除する。
・タブ、改行、連続空白を半角スペース1文字にする。
・検索用文字列では英字を小文字化する。

表示用文字列と比較・検索用文字列を混同しない。

元の表示文字列を必要以上に変更しない。

5.5 日付処理

日付処理関数は、現在時刻へ暗黙依存させない。

次の関数を実装する。

・parseExcelDate(value)
・parseJapaneseDateString(value)
・formatIsoDate(value)
・getLatestPermitDate(facilities)
・getDateRangeFromBaseDate(baseDate, days)
・isWithinPeriod(date, baseDate, days)

対応候補:
・YYYY-MM-DD
・YYYY/MM/DD
・YYYY年M月D日
・Excel日付シリアル値

令和などの和暦が含まれる場合:
対応できる範囲で明示的な変換ロジックを実装する。

対応できない値:
推測せずnullにし、検証結果に記録する。

タイムゾーンによる日付の前日化を避けるため、日付だけの値をUTC日時へ不用意に変換しない。YYYY-MM-DDの文字列として扱う。

5.6 データ検証

validate-data.tsを作成する。

次を検査する。

・レコード数が0ではない
・IDが空でない
・IDが一意
・施設名、住所、許可番号がすべて空のレコードがない
・permitDateがnullまたはYYYY-MM-DD
・expirationDateがnullまたはYYYY-MM-DD
・将来の異常日付がない
・極端に古い日付がない
・重複候補件数
・列マッピング結果
・前回データとの件数差

件数差に関する安全策:
前回データが存在する場合、レコード数が前回比で50%以上減少したときは、自動更新を失敗させる。

ただし、この閾値はscripts/config.tsなどで変更可能にする。

初回実行:
previous.jsonが存在しない場合は差分安全策をスキップし、その旨をログに出す。

検証結果:
人間が読めるログと、機械可読なvalidation-report.jsonの両方を生成する。

validation-report.jsonは一時成果物としてよく、公開サイトに配置しなくてもよい。

5.7 更新処理の安全性

データ更新は一時ディレクトリで行う。

手順:
1. XLSXを一時ディレクトリへダウンロード
2. SHA-256を計算
3. XLSXを解析
4. JSONへ変換
5. スキーマ検証
6. 重複検査
7. 前回データとの比較
8. diff.json生成
9. すべて成功した場合のみpublic/dataを更新
10. 失敗した場合は既存の正常データを変更しない

途中で失敗してもcurrent.jsonが空ファイルにならないようにする。

ファイル書き込みは、一時ファイル作成後のrenameによる置換を基本とする。

ダウンロード処理:
・HTTPステータスを検証する。
・Content-Typeだけを信用しない。
・ファイルサイズが0でないことを確認する。
・XLSXとして開けることを確認する。
・タイムアウトを設定する。
・一時的な通信エラーは最大3回まで指数バックオフで再試行する。
・エラーメッセージに秘密情報を含めない。

6.1 CIワークフロー

.github/workflows/ci.ymlを作成する。

実行条件:
・mainブランチへのpush
・mainブランチへのpull_request
・workflow_dispatch

実行内容:

3. npm ci
4. npm run format:check
5. npm run lint
6. npm run typecheck
7. npm run test:unit
8. npm run test:coverage
9. npm run build
10. Playwright用ブラウザを導入
11. npm run test:e2e

失敗時:
・Playwrightレポート
・スクリーンショット
・trace
をGitHub Actionsのartifactとして保存する。

6.2 データ更新ワークフロー

.github/workflows/update-data.ymlを作成する。

実行条件:
・workflow_dispatch
・cronによる定期実行

データは年4回程度の更新が想定されるため、週1回程度の確認でよい。cronはUTCで実行されることをコメントで明記する。

実行内容:
1. checkout
2. Node.jsセットアップ
3. npm ci
4. npm run data:update
5. npm run data:validate
6. npm run test:unit
7. npm run build
8. git diffで変更確認
9. 変更がある場合のみブランチ作成
10. Pull Request作成

安全性を優先し、データ更新結果をmainへ直接pushしない。
可能であればGitHub CLIを使ってPull Requestを作成する。
必要なpermissionsを最小限で明示する。

同じdataVersionのPull Requestを重複作成しない。

データ取得や検証に失敗した場合:
・ワークフローを失敗させる。
・既存データを更新しない。
・原因がログから分かるようにする。

6.3 デプロイワークフロー

.github/workflows/deploy.ymlを作成する。

実行条件:
mainブランチへのpush

デプロイ前に最低限次を通す。

・npm ci
・npm run typecheck
・npm run test:unit
・npm run build

GitHub公式のPages向けAction構成を使用する。
Viteのbase設定をGitHub Pagesのリポジトリ名に対応させる。

ローカル開発ではbaseを「/」として扱えるようにする。

・タイムゾーンに影響されないこと

ID生成:
・同じ入力から同じID
・異なる許可番号から異なるID
・許可番号欠損時
・空白や全角半角の差を正規化できること
・入力オブジェクトを変更しないこと

検索:
・単語検索
・複数語AND検索
・施設名検索
・住所検索
・業種検索
・空検索
・該当なし

フィルタ:
・業種
・細分類
・期間
・住所
・複合条件
・条件リセット

並び順:
・許可日の新しい順
・許可日の古い順
・日付nullの扱い
・同一日付で施設名順
・元配列を破壊しないこと

集計:
・業種別
・年月別
・最近30日、90日、180日
・空配列
・不正日付を除外

差分:
・追加
・削除候補
・変更
・変更なし
・許可番号欠損
・同一許可番号で内容変更
・重複レコード
・入力順が変わっても結果が変わらないこと

localStorage:
・登録
・解除
・重複登録
・破損JSON
・localStorage利用不可

7.3 E2Eテスト

Playwrightを使用する。

ネットワーク上の実データに依存しない。
テスト用fixtureを使用する。

最低限のシナリオ:
1. トップページが表示される
2. データ注意書きが表示される
3. 施設一覧を開ける
4. キーワード検索ができる
5. 業種で絞り込める
6. 検索と業種の複合条件が動く
7. 並び順を変更できる
8. 施設詳細を開ける
9. ブラウザバックで一覧状態へ戻れる
10. URL共有用クエリから状態を復元できる
11. お気に入りを登録できる
12. 再読み込み後もお気に入りが残る
13. 該当なし表示が出る
14. 存在しない施設IDでエラー画面が出る
15. スマートフォン幅で主要機能が操作できる
16. GitHub Pages相当のサブパスでアセットが読み込める

外部地図リンク:
実際の外部サイトへ移動せず、href、target、relが正しいことを検証する。

E2Eテストでは日時を固定するか、データ内の最大日付を基準にする。

8. UI/UX仕様
==================================================

デザイン方針:
・行政サイトの複製ではなく、市民向けの見やすいデザイン
・白を基調とする
・アクセントカラーは富山の水や自然を想起させる青または青緑
・装飾を増やしすぎない
・1画面に情報を詰め込みすぎない
・スマートフォンを優先する

ヘッダー:
・サービス名
・最近の施設
・施設を探す
・ダッシュボード
・前回との差分
・お気に入り
・データについて

施設カード:
・施設名を最も強調
・業種をラベル表示
・許可年月日を表示
・住所を表示
・営業者名や許可番号を過度に強調しない
・カード全体をリンクにせず、明確な「詳細を見る」を設置してもよい

状態表示:
・読み込み中
・データ取得失敗
・データ0件
・検索結果0件
・localStorage利用不可
・データ更新あり

データ取得失敗時:
画面全体を真っ白にしない。
再読み込みボタンと、データが読み込めなかった旨を表示する。

==================================================
9. セキュリティとプライバシー
==================================================

・元データに存在しない個人情報を推測、生成、補完しない。
・施設名や営業者名を使って外部サイトを自動検索しない。
・住所から緯度経度を外部APIで自動取得しない。
・Google MapsなどのAPIキーをソースコードへ含めない。
・innerHTMLを使用しない。
・利用者入力はReactの通常のエスケープ機構で表示する。
・URLパラメータをHTMLとして挿入しない。
・外部リンクにはnoopener noreferrerを設定する。
・依存パッケージを必要最小限にする。
・npm auditの結果を確認する。
・秘密情報をGitHub Actionsログへ出力しない。
・本アプリは公開情報を再掲するものであることを明示する。
・元データの訂正はアプリ運営者ではなくデータ提供者へ確認すべきことを明記する。

==================================================
10. 地図機能の扱い
==================================================

初期MVPでは、施設住所から地図サービスを開くリンクのみを必須とする。

緯度経度が元データに含まれないため、地図上への正確なポイント表示を推測で実装しない。

次のいずれかが将来可能になった場合に限り、地図表示を追加できる構造にする。

・公式データに緯度経度が追加された
・別途、検証済みのジオコーディング済みデータを用意した
・GitHub Actionsでジオコーディングし、結果を人間が確認した

位置情報がない段階で、住所文字列を適当な座標へ配置しない。
